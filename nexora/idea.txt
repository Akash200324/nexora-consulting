- assessment answers
- score
- qualification route
- UTM attribution
- booking status
- CTA interactions

Systeme.io should act as the external CRM/marketing layer.

DO NOT replace any existing Django data with Systeme.io data.

--------------------------------------------------
PHASE 1 — INSPECT BEFORE CODING
--------------------------------------------------

First inspect:

1. Existing AssessmentSubmission model
2. Existing UTM fields and helpers
3. Existing FGA/BPA qualification logic
4. Existing Calendly booking flow
5. Existing BPA WhatsApp flow
6. Existing settings/environment configuration
7. Existing requirements/documentation for Systeme.io
8. Existing project architecture and naming conventions

Also inspect the current Systeme.io Public API documentation before choosing endpoint URLs or request formats.

Do not guess API endpoints.

Do not modify code during this inspection phase.

Report:
- exact integration requirements
- required Systeme.io resources
- required contact fields
- required tags
- required custom fields
- exact events that should trigger synchronization
- API endpoints needed
- files that will need modification

Then proceed with implementation only after confirming the architecture is consistent with the documented requirements.

--------------------------------------------------
PHASE 2 — CREATE A SYSTEME.IO SERVICE LAYER
--------------------------------------------------

Create a dedicated integration/service module.

For example:

core/integrations/systeme_io.py

Use a reusable service/class rather than putting API requests directly inside Django views.

The service should handle:

- authentication
- API base URL
- HTTP requests
- timeout handling
- response validation
- API error handling
- logging
- create/update contact
- find existing contact by email
- assign tags
- retrieve/create/use required custom fields if appropriate

Use the existing project's dependencies and coding style.

Do NOT introduce unnecessary packages if Python's existing HTTP tooling/dependencies are sufficient.

--------------------------------------------------
PHASE 3 — CONFIGURATION
--------------------------------------------------

Add configuration through environment variables.

At minimum:

SYSTEME_IO_API_KEY

Do not expose this value anywhere in:
- templates
- JavaScript
- API responses
- logs
- Git
- admin pages

Make the application fail safely if the API key is missing.

The website itself must continue working if Systeme.io is temporarily unavailable.

--------------------------------------------------
PHASE 4 — CONTACT SYNCHRONIZATION
--------------------------------------------------

When the appropriate lead event occurs according to the client specification:

1. Take the existing AssessmentSubmission.
2. Validate that it contains the required contact information.
3. Find the corresponding Systeme.io contact by email if possible.
4. Create the contact if it does not exist.
5. Update the contact if it already exists.
6. Assign the appropriate tags.
7. Populate the required custom fields.

Do NOT create duplicate contacts every time the same user interacts with the website.

Email should be treated as the primary contact matching field unless the Systeme.io API/documentation requires another approach.

--------------------------------------------------
PHASE 5 — DATA MAPPING
--------------------------------------------------

Create a centralized mapping between Django and Systeme.io.

Potential fields:

Django → Systeme.io

full_name → contact name
email → contact email
phone → contact phone

assessment reference → custom field
assessment score → custom field
qualification route → custom field
FGA/BPA → qualification custom field/tag

first_utm_source → custom field
first_utm_medium → custom field
first_utm_campaign → custom field
first_utm_content → custom field
first_utm_term → custom field

last_utm_source → custom field
last_utm_medium → custom field
last_utm_campaign → custom field
last_utm_content → custom field
last_utm_term → custom field

IMPORTANT:
Only implement fields that are actually required by the client specification and supported by the Systeme.io account/API.

Do not create unnecessary custom fields.

--------------------------------------------------
PHASE 6 — TAGGING
--------------------------------------------------

Use centralized tag names/constants.

For example, only if supported by the actual specification:

Nexora Consulting
FGA Qualified
BPA Qualified
Assessment Completed
FGA Booked
BPA Strategy Call

Do not blindly create all of these.

First determine which tags are actually required.

Avoid duplicate tag creation or repeated assignment.

--------------------------------------------------
PHASE 7 — EVENT FLOW
--------------------------------------------------

Do NOT synchronize every page view.

The integration should be tied to meaningful conversion events.

The likely flow is:

Assessment completed
        ↓
Create/update Systeme.io contact
        ↓
Add qualification tag
        ↓
Store assessment information

Then:

FGA booking confirmed
        ↓
Update Systeme.io contact/tag

BPA strategy-call/WhatsApp conversion
        ↓
Update Systeme.io contact/tag

BUT:

Use the actual client specification to determine which of these events should be implemented.

Do not assume an event is required merely because it exists in the Django application.

--------------------------------------------------
PHASE 8 — CALENDLY
--------------------------------------------------

Existing Calendly webhook logic is the source of truth for actual booking status.

Do NOT mark a Systeme.io contact as "booked" merely because the Calendly widget was viewed or a date/time was selected.

Only use the existing successful Calendly webhook event for an actual booking-related synchronization if the specification requires it.

Do not modify existing Calendly webhook behavior unnecessarily.

--------------------------------------------------
PHASE 9 — BPA
--------------------------------------------------

Do not bypass existing BPA assessment protection.

Existing logic must remain:

No valid completed assessment
        ↓
Cannot access strategy-call flow

Valid assessment
        ↓
BPA strategy call / WhatsApp

If Systeme.io synchronization is required for BPA, use the existing AssessmentSubmission and CTAInteraction data.

Do not weaken or bypass the current server-side protection.

--------------------------------------------------
PHASE 10 — FAILURE HANDLING
--------------------------------------------------

Systeme.io must NOT become a single point of failure for the website.

If Systeme.io API fails:

- Django should still save the assessment.
- Django should still save UTM data.
- Existing assessment result should still work.
- Existing FGA/BPA routing should still work.
- Existing Calendly flow should still work.
- Existing BPA WhatsApp flow should still work.

Log the integration failure safely without logging the API key.

Prefer a controlled retry/failed-sync mechanism if the existing architecture supports it.

Do not silently lose a lead.

If necessary, create a local synchronization status/error record so failed Systeme.io synchronization can be retried later.

Do not add a complex queue system unless the project actually needs it.

--------------------------------------------------
PHASE 11 — TESTING
--------------------------------------------------

Add automated tests for:

1. API key missing
2. Successful contact creation
3. Existing contact update
4. Duplicate prevention
5. Tag assignment
6. Custom field mapping
7. FGA qualification mapping
8. BPA qualification mapping
9. UTM mapping
10. Systeme.io API failure
11. Existing assessment still works when Systeme.io is unavailable
12. Calendly webhook behavior remains unchanged
13. BPA protection remains unchanged
14. API key is never exposed in logs/responses

IMPORTANT:

Do not make real Systeme.io API calls from automated tests.

Mock the external API.

For manual integration testing, provide a separate safe test procedure using the development Systeme.io account.

--------------------------------------------------
PHASE 12 — MANUAL TEST MODE
--------------------------------------------------

Create a safe way to verify the integration locally.

For example, an internal management command or development-only test endpoint if appropriate.

It should allow me to test:

Django AssessmentSubmission
        ↓
Systeme.io API
        ↓
Contact created/updated
        ↓
Tag assigned
        ↓
Custom fields populated

Do not expose a testing endpoint publicly in production.

--------------------------------------------------

- UTM last-touch tracking
